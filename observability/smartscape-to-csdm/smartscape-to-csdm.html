Nothing on the platform side is scripted: platform features, connector configuration and a naming convention at the source; the application asserts its key as OpenTelemetry resource attributes. Every line is a fact from the connector's own query and transform map, from its runs against a two-host estate, or from a test of the tenant. How the connector populates the CMDB

01

The connector reads Smartscape through a time window

Each data source is one smartscapeNodes query. The first run covers a configurable number of days, later runs the time since the last run. A node alive at any moment in the window is imported, stale identities included; retirement follows after the configured number of days without a sighting.

02

The chain written depends on how the service was detected

A OneAgent service carries edges to its process and to the services it calls. An OpenTelemetry service carries an edge to its host only. The shipped transform map has no host entity; one conditional class on that edge closes the gap.

03

Identity is the Smartscape id with a connection prefix

Every CI gets a sys_object_source row keyed <alias sys_id>|||<Smartscape id>. The Event Management push connector builds the same key for 3rd-generation events, so event binding depends on this connector having run.

04

Every process becomes a CI

One application CI per uncontainerised process with an executable path, OneAgent's own processes included, each related to its host. Classification comes from Discovery's process classifiers: Gunicorn, Nginx and PostgreSQL get typed classes.

05

The service model is joined by configuration

The detection rule's name template carries service.namespace and deployment.environment into the service name. The Service map, extended in IntegrationHub ETL, splits the name, looks up the Business Application and the offering, and writes the CSDM relationships on every import. A Dynamic CI Group per technical offering holds the hosts by query.

Preconditions

P0

Out of the box, no platform code

Every mechanism on the platform side is a documented platform feature: the detection rule's name template, the connector's Service map extended in IntegrationHub ETL, Dynamic CI Groups over CMDB groups, CI relationships. No business rule, no scheduled script, no custom table. The application contributes its key as resource attributes in its deployment configuration. Scripted alternatives were written, recorded and not used.

P1

Model first, then open the pipe

The Business Application, the services and the offerings existed, and the naming contract was agreed on both sides, before the first run. The connector fills a frame; it does not propose one. Opened in the other order, the CMDB receives everything and the modelling becomes an investigation of what arrived, which does not scale past a few dozen services.

P2

Green field

The CMDB held nothing but the connector's own CIs and the hand-built CSDM v5 model. Every relationship above is the first one its CIs ever had. A CMDB already fed by several integrations starts with reconciliation and precedence, not with the bridge.

P3

One source per class

The connector is the only discovery source for hosts, processes and services, so IRE has nothing to arbitrate. Add a second source for the same classes and the identification rules, not the map, decide who wins.

P4

The naming contract holds on both sides

Service name <namespace> <service> <environment>, offering name <namespace> <environment>. A lookup that finds no row writes nothing and reports nothing; watching that silence is the operational cost.

P5

Two hosts, three applications

Small enough to read every row. The mechanisms scale by configuration; the evidence does not claim to.

Where the SaaS connector departs from the classic-connector guides

The integration guides written for the classic connector sayThe SaaS connector shows
Services come from OneAgent-instrumented processesOpenTelemetry-ingested services carry a host edge only
Direct service → host is the fallback path on SaaSThe shipped map has no host entity; the fallback is an extension of the map
The SaaS chain names PROCESS_GROUP_INSTANCESmartscape holds PROCESS; the CI is one per process, keyed on the PROCESS id
The Business Application key travels as a tag ruleNo tag rules on a 3rd-generation tenant; cloud host tags arrive as key-value records. The key lives on the spans: the Smartscape service node carries neither tags nor attributes, and a manual tag set in the classic UI does not reach it. Closed by convention: the detection rule's name template carries the key into the service name, and the extended Service map writes the relationships
The cloud anchor is a VM entityThe host carries the cloud resource id; the VM resource is a Smartscape node outside every data source; no VM CI exists to link
A stale service is a staleness case to handleStale services are imported whenever they fall inside the window; retirement follows after the configured number of days

TermMeaning here

Service Graph ConnectorThe ServiceNow Store application that reads Smartscape per node type, stages each node as JSON and writes CIs and relationships through IRE
Data source, import setOne Load-by-Script data source per node type; each run stages rows into an import set, then the transform map runs
IntegrationHub ETL, Robust Transform EngineThe declarative transform layer: prepare operations (Split, Concatenation, Table Lookup), conditional classes, conditional relationships
IRE, identification ruleThe Identification and Reconciliation Engine: matches a payload to an existing CI by the class's identification rule, creates or updates, records the source
Native key, object sourceThe source's own id for a record, stored in sys_object_source as <alias sys_id>|||<Smartscape id>; an entity mapping only a native key resolves an existing CI without touching its attributes
Calculated application serviceThe CI class the connector uses for a Smartscape service: cmdb_ci_service_calculated, a service instance populated by an integration
CSDM v5ServiceNow's Common Service Data Model: Business Application, Business Service and its Business Service Offerings (BSO), Technology Management Service and its Technical Service Offerings (TSO), service instance, Dynamic CI Group. The board shows the three tables above the service instance as one simplified box, Services and Offerings each holding their business and technical classification; the connector writes to the Business Application and the BSO, the TSO holds the Dynamic CI Group, and the two parent services receive nothing
Dynamic CI Group, CMDB groupA CI in cmdb_ci_query_based_service whose members come from a CMDB group; the group is populated by an encoded query over a class
OneAgent service, OpenTelemetry serviceHow Dynatrace came to know the service, not where OneAgent runs. OneAgent is on every host; a service is "OneAgent" when the agent deep-monitors its process (Java, .NET, Node.js, Go, PHP), "OpenTelemetry" when the application exports spans to the agent's local OTLP endpoint (Python here). The chain the connector writes differs between the two

Resource attributesOpenTelemetry attributes on every span from an application, here service.namespace and deployment.environment
